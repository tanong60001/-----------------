## หลักฐานการทดสอบ

- `node --test tests/*.test.js` ผ่าน 45/45 รายการ ครอบคลุมการขาย สต็อก ยอดเงิน รายงาน ลิ้นชัก และส่วนอื่นที่มีชุดทดสอบเดิม
- เพิ่มทดสอบการอ่านสินค้าหนึ่งรอบต่อบิล การผูก ID บิลจริง สต็อกไม่พอ การเปลี่ยนสต็อกจากอีกเครื่อง การส่งบันทึกซ้ำ และการรวมคำขอซิงก์
- ตรวจ syntax ของ JavaScript ที่แก้และตรวจ diff whitespace ผ่าน
- แปลง TypeScript ของ Edge Function ทั้ง source และไฟล์ deploy ด้วย esbuild ผ่าน (ตรวจไวยากรณ์ ไม่ใช่การทดสอบ Deno runtime)
- ตรวจหน้าล็อกอินบน Edge headless ที่ 320×568, 360×640, 390×844, 430×932, 844×390, 390×320 และ 1280×800: การ์ด/ช่อง PIN/ปุ่มอยู่กึ่งกลาง ช่อง PIN กว้างเท่ากัน ไม่ล้นด้านข้าง จอสั้นเลื่อนเข้าถึงเนื้อหาได้
- เปิดโปรแกรมที่โหลดทุกโมดูลด้วยฐานข้อมูลจำลองบนจอ 390×844: ไม่พบ JavaScript page error และหน้าล็อกอินอยู่กึ่งกลาง
- ทดสอบเพิ่มสินค้าทั่วไป 100 ครั้งผ่านโปรแกรมที่โหลดทุกโมดูล: จำนวนครบ 100 ป้ายจำนวนถูกต้อง ไม่เรียกสร้างกริดใหม่ และเก็บ DOM การ์ดเดิมไว้
- ทดสอบ observer ของสินค้าตามสูตรด้วย DOM จริง: ตกแต่งเสร็จแล้วหยุดนัด frame ซ้ำ

ผลด้านความเร็วเป็นหลักฐานว่าเอางานและคำขอที่ไม่จำเป็นออกแล้ว ยังไม่ได้จับเวลาบันทึกบิลกับฐานข้อมูลจริง จึงไม่อ้างเปอร์เซ็นต์ความเร็วหรือรับรองเวลาเป็นวินาที

## ความหมายของตัวเลขในภาพและงานฝั่งระบบจริง

1.136 / 1 GB คือยอด log ที่ระบบรับเข้าสะสมในรอบ ไม่ใช่ขนาดไฟล์โปรแกรมหรือขนาดตาราง `log_กิจกรรม` การลดคำขอ API และข้อความจาก Edge Function ช่วยลด log ใหม่ ส่วน console ของเว็บในเบราว์เซอร์ไม่ได้ลดโควตานี้โดยตรง

Supabase ระบุว่ายอดนี้รวมหลายบริการ เช่น Postgres, API, Auth, Storage, Realtime และ Edge Functions ตาม [เอกสาร Logs Ingest](https://supabase.com/docs/guides/platform/manage-your-usage/logs-ingest) จึงยังระบุไม่ได้จากภาพเพียงภาพเดียวว่าบริการใดเป็นต้นเหตุหลัก และไม่สามารถรับรองว่าจะต่ำกว่า 1 GB หลังแก้โค้ดโดยยังไม่มีข้อมูลจากระบบจริง

หลังเผยแพร่ให้ดู Usage และ Logs Explorer แยกบริการของโปรเจกต์นี้ แล้วเทียบอัตราเพิ่มใน 24–48 ชั่วโมงกับจำนวนผู้ใช้/จำนวนขายใกล้เคียงกัน ตรวจ webhook ที่ยิงซ้ำและตรวจการตั้งค่า Postgres ด้วยคำสั่งอ่านอย่างเดียวต่อไปนี้:

```sql
SELECT name, setting, unit
FROM pg_settings
WHERE name IN (
  'log_statement', 'log_min_duration_statement', 'log_min_messages',
  'log_connections', 'log_disconnections', 'pgaudit.log', 'pgaudit.role'
)
ORDER BY name;
```

ยังไม่ได้เปลี่ยนค่าฐานข้อมูล เพราะต้องดูค่าปัจจุบันและแหล่ง log ที่ใช้มากก่อน ยอดที่สะสมเกินไปแล้วจะไม่ลดลงจากการแก้โค้ดนี้

## ข้อจำกัดที่ยังมีอยู่ในโครงสร้างเดิม

การสร้างบิล ตัดสต็อก เขียนประวัติ เงินสด และยอดลูกค้ายังเป็นหลายคำขอแยกกัน การตรวจ stock เดิมก่อน update และการทำเครื่องหมายบิล “รอตรวจสอบ” เมื่อเกิดข้อผิดพลาดยังอยู่ครบ แต่ไม่ได้ทำให้ทุกขั้นตอนเป็น transaction เดียว หากต้องการให้ความผิดพลาดกลางทาง rollback ได้ทั้งหมด ต้องพัฒนาฟังก์ชันฐานข้อมูลสำหรับการขายและทดสอบกับ schema จริงเพิ่มเติม

ยอดรวมลูกค้ายังมีบางเส้นทางที่อ่านยอดแล้วเขียนกลับ จึงต้องพิจารณาการขายพร้อมกันหลายเครื่องแยกจากงานลด log ครั้งนี้ ส่วนจำนวนโมดูลและการ override ฟังก์ชันหลายชั้นยังเป็นต้นทุนการโหลดและบำรุงรักษา ควรรวมเส้นทาง POS/checkout ในงานปรับโครงสร้างถัดไป
